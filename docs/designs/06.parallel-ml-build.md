# Parallel ML-on Implementation Flow — xcvu9p

**Status:** implemented; measured results recorded below
**Date:** 2026-11-22
**Branch:** `fangrui/vu9p-parallel-ml-build`
**Scope:** `xcvu9p-flgb2104-2-e`, Vivado 2025.2, 100 MHz NPU fabric

## 1. Why

The 100 MHz engine closes with sub-0.1 ns margin (WNS +0.056 ns on the
A+B+P bitstream).  Timing closure therefore benefits from the best placement,
not merely the first placement that routes.  At the same time the previous flow
was slow:

- placement was run ML-off, single-threaded, because the ML model had crashed;
- one implementation candidate was built at a time;
- the project implementation run silently used
  `set_param general.maxThreads 2`, because that is what Vivado writes into the
  generated `impl_1` run script, regardless of the parent process's
  `general.maxThreads`;
- `launch_runs impl_1 ... -jobs N` was being used as if `-jobs` parallelized a
  single run.  It does not: `-jobs` is the number of **parallel runs**, and a
  single run remains governed by `general.maxThreads`.

Measured with the same post-opt checkpoint:

| flow | place elapsed | peak memory | post-place WNS |
|:--|--:|--:|--:|
| ML off, 1 thread (final A+B+P) | 42:45 | ~12.0 GB | +0.190 ns |
| ML on, 8 threads | **25:05** | **13.25 GB** | **+0.272 ns** |
| ML on, 8 threads + `-ultrathreads` | SIGSEGV at ~5:20 | ~10.5 GB | — |

ML-on placement is ~1.7x faster than the old ML-off single-threaded placement
and uses only ~1.3 GB more.  The measured 13.25 GB peak is far below the host's
60 GiB, so memory is not the limiting resource for this design.

`-ultrathreads` is **not used**: both runs that enabled it died with SIGSEGV in
`HAPLFSimPLFlow::collectControlSetInfo()` / `adjustFFArea()` while the
per-SLR worker thread (`simplFlowDoIterSLRThreadWorker`) was collecting
control-set info in Phase 2.5 Global Place Phase1.  The stack is a data race in
Vivado 2025.2's per-SLR placement, not an ML-model or memory failure.  Plain
8-thread placement is stable and faster overall.

## 2. Host and toolchain facts

- Host: Ubuntu 26.04.1, glibc 2.43, AMD Ryzen 7 5800X (8 cores / 16 threads),
  60 GiB RAM, 64 GiB `/swapfile`.
- Vivado: 2025.2, run in the `vivado-runtime:22.04` container (glibc 2.35).
  Vivado 2025.2 officially supports Ubuntu 22.04/24.04, not 26.04; the host
  glibc makes the host binary abort in `HUTFileUtils`, so the container is the
  supported workaround.  Do not run Vivado directly on the 26.04 host and do
  not add host ncurses symlinks; the 22.04 image already has the required
  libraries.
- Design peak memory (implementation): **~13.4 GB** (route + bitstream).
- The container must run with `--ipc=host`: Docker's default `/dev/shm` is
  64 MB, while the host's is 31 GB.  A 64 MB shared-memory segment is a known
  source of multi-threaded application crashes; the runner uses `--ipc=host`.
- No OOM kills were observed.  The observed failures are Vivado SIGSEGVs
  (`Abnormal program termination (11)`), not the Linux OOM killer.  A larger
  swap file or a lower `general.maxThreads` does not fix a SIGSEGV; the flow
  must checkpoint and retry.
- `general.maxThreads` on Linux accepts 1..8.  `-ultrathreads` is available for
  UltraScale+ SSI devices (xcvu9p is SSI), but on this design/Vivado 2025.2 it
  consistently SIGSEGVs in `HAPLFSimPLFlow::collectControlSetInfo`; it is
  opt-in only and not used by the default flow.

## 3. ML models

Vivado 2025.2 enables two ML estimators by default:

| parameter | default | meaning |
|:--|:--:|:--|
| `place.3d.congestionML` | `8193` | ML congestion estimation (3D placer) |
| `place.disableMlde` | `0` | ML delay estimation is enabled |

AMD's WP532 reports that the ML delay estimator improves delay-estimate
accuracy from ~65.5% to ~98%; the congestion estimator is used by placement to
avoid routing hotspots.  On this multi-SLR part the GTY/PCIe-left-edge region
is the sensitive area; the proven place directive remains
`ExtraTimingOpt`.

The flow therefore defaults to **ML on**:

```tcl
set_param place.3d.congestionML 8193
set_param place.disableMlde 0
```

`NPU_ML=off` remains the fallback (`0` / `1`), and `hybrid` keeps the
congestion model but disables ML delay estimation.

## 4. Architecture

The implementation is split into three checkpointed stages so a failed route
does not discard a successful placement:

```
hw_platform_opt.dcp
   │
   ├─ place 0 (ExtraTimingOpt,     ML on,  8 threads)
   ├─ place 1 (SSI_SpreadLogic_high, ML on, 8 threads)
   └─ place 2 (ExtraTimingOpt,     ML off, 2 threads)  ← safety/QoR
          │  pick best post-place WNS (all are routed)
          ├─ phys_opt candidate 0
          ├─ phys_opt candidate 1
          └─ phys_opt candidate 2
                 │  each writes physopt.dcp
                 ├─ route candidate 0 (Default)
                 ├─ route candidate 1 (Default)
                 └─ route candidate 2 (Default)
                        │  pick best post-route WNS, WNS >= -1.0 ns
                        └─ copy best candidate.bit -> top_npu_vu9p.bit
```

Each candidate is an independent Vivado process:

- **place**: open the post-opt DCP, set threads/ML, run
  `place_design -directive <d>`, write `placed.dcp`, report post-place timing.
- **physopt**: open `placed.dcp`, run `phys_opt_design`, write `physopt.dcp`.
- **route**: open `physopt.dcp`, run `route_design`, write `routed.dcp`, check
  unrouted nets, report post-route timing, apply the WNS gate, write the
  bitstream.

The host launcher `tool/fpga/parallel_impl.py` sizes concurrency from
`MemAvailable` and physical cores:

- budget **16 GB per candidate** (measured 13.5 GB peak plus headroom);
- reserve **6 GB** for the OS;
- ~**2.5 physical cores** per candidate (measured 2.4 cores average);
- default **3 candidates**: two ML-on placements plus one ML-off 2-thread
  safety placement; 60 GiB / 8 cores runs them comfortably.
- On a 32 GiB host the same model clamps to 1; on 64 GiB it clamps to 3.

The three stages run concurrently within each stage, not across stages.  This
keeps the peak at ~3 × 13.5 GB and still gives three independent placements and
three independent routes.  Stage 1 is bounded by the ML-off safety placement
(~35 min), stage 3 by the safety route (~48 min).

## 5. Crash handling

Vivado 2025.2 is not stable on this design.  Three failure shapes are observed:

1. ML model teardown: `LgbmTree::~LgbmTree` /
   `HCMBoostTreeEstimator::~HCMBoostTreeEstimator`.
2. Route timing updates: `Abnormal program termination (11)` at a
   `... Update Timing` phase, sometimes with the ML estimators already off.
3. `-ultrathreads` per-SLR placement race:
   `HAPLFSimPLFlow::collectControlSetInfo` in
   `simplFlowDoIterSLRThreadWorker` (see §7).  It is opt-in only and is not
   used by the default flow.

None is an OOM kill; peak memory remains ~13 GB.  The launcher therefore:

- checkpoints after place and phys_opt;
- treats any non-zero exit, timeout, `SIGSEGV`, `LgbmTree`, `HCMBoost`, or
  `Abnormal program termination` as a retryable candidate failure;
- retries placement with ML off (4 threads, then 1 thread);
- retries routing from the existing `physopt.dcp` with ML off and 2 threads
  (the proven fallback), using `Default`;
- copies any `hs_err_pid*.log` into the candidate directory before the next
  attempt;
- keeps the old ML-off single-thread recipe
  (`ip/vivado/xcvu9p/scripts/impl_1thread_noml.tcl`) as a known-good fallback
  if every candidate fails.

The retry never re-runs synthesis or placement for a route-only failure.

## 6. Commands

Prerequisites: `top.sv` built (`make build`) and the project bootstrapped
(`setup_platform.tcl` run once).

One command, full flow:

```bash
tool/fpga/build_vu9p_parallel.sh \
  --jobs 3 \
  --threads 8 \
  --ml on
```

The default `--place-specs` is
`ExtraTimingOpt:on:8,SSI_SpreadLogic_high:on:8,ExtraTimingOpt:off:2`:
two ML-on candidates and one ML-off 2-thread safety candidate.  For the fastest
single bitstream (accepting the ~−0.055 ns ML-on route) use one ML-on
candidate:

```bash
tool/fpga/build_vu9p_parallel.sh --jobs 1 \
  --place-specs ExtraTimingOpt:on:8
```

It runs:

1. `make build` (unless `--skip-chisel`);
2. `build_npu_vu9p.tcl` with `NPU_STOP_AFTER_OPT=1` in the 22.04 container;
3. `parallel_impl.py` in split mode.

Reuse an existing post-opt checkpoint:

```bash
tool/fpga/build_vu9p_parallel.sh --skip-chisel --skip-synth
```

Direct launcher use / dry run:

```bash
python3 tool/fpga/parallel_impl.py --dry-run --jobs 3
python3 tool/fpga/parallel_impl.py \
  --checkpoint ip/vivado/xcvu9p/prj/prj.runs/impl_1/hw_platform_opt.dcp \
  --jobs 3 --threads 8 --ml on \
  --place-specs ExtraTimingOpt:on:8,SSI_SpreadLogic_high:on:8,ExtraTimingOpt:off:2 \
  --route-directives Default
```

The launcher writes `result.env` per candidate, `summary.json`, per-attempt
Vivado logs, and copies the winning bitstream to
`ip/vivado/xcvu9p/top_npu_vu9p.bit`.

Synthesis alone (parallel OOC IP jobs):

```bash
NPU_STOP_AFTER_OPT=1 VIVADO_JOBS=4 NPU_MAX_THREADS=8 \
  vivado -mode batch -source ip/vivado/xcvu9p/scripts/build_npu_vu9p.tcl
```

The legacy single-shot project flow is still available:

```bash
NPU_MAX_THREADS=8 NPU_ML=on VIVADO_JOBS=4 \
  vivado -mode batch -source ip/vivado/xcvu9p/scripts/build_npu_vu9p.tcl
```

Its `STEPS.*.TCL.PRE` hooks override the generated run's
`general.maxThreads 2`.

## 7. Measured results

### Placement experiment (2026-11-22)

All three candidates ran concurrently from the same `hw_platform_opt.dcp`.
`ml_plain` and `ml_ultra` used `ExtraTimingOpt`; `ssi_ultra` used
`SSI_SpreadLogic_high`.  All had ML on and `general.maxThreads=8`.

| candidate | `-ultrathreads` | elapsed | peak | post-place WNS | result |
|:--|:--:|--:|--:|--:|:--|
| `ml_plain` | no | **25:05** | **13.25 GB** | **+0.272 ns** | pass |
| `ml_ultra` | yes | SIGSEGV at 5:20 | 10.5 GB | — | crash |
| `ssi_ultra` | yes | SIGSEGV at 5:48 | 10.5 GB | — | crash |

The crash stack is the per-SLR placement worker:

```
HAPLFSimPLFlow::simplFlowDoIterSLRThreadWorker
  -> HAPLFSimPLFlow::doOneIterBody
     -> HAPLFSimPLFlow::adjustFFArea
        -> HAPLFSimPLFlow::collectControlSetInfo
           -> std::_Hashtable<...>::operator=
```

This is a Vivado 2025.2 data race in the `-ultrathreads` per-SLR placement,
not an ML or memory failure.  Plain 8-thread ML-on placement is stable,
25 minutes, and produces a better post-place WNS (+0.272 ns) than the old
ML-off recipe (+0.190 ns).

### Route validation

### Route validation (2026-11-22)

The ML-on placement was phys_opt'ed (3:42 stage, 47 s `phys_opt_design`) and
routed three ways.  A route from the known-good final placement was included
for comparison.

| candidate | placement | route | elapsed | post-route WNS | result |
|:--|:--|:--|--:|--:|:--|
| `route_ml_default` | ML on, 25:05 | `Default`, 8t | **36:15** | **−0.055 ns** | pass, 0 unrouted |
| `route_known_default` | known-good ML off | `Default`, 8t | 48:10 | **+0.056 ns** | pass, 0 unrouted |
| `route_ml_explore` | ML on | `Explore`, 8t | 28:57 | — | fail: `[Route 35-557]` overlap at `SLICE_X115Y88` |

The ML-on flow is faster end-to-end but gives up ~0.11 ns of post-route
margin:

- **Fast path** (one ML-on candidate): synth/opt 22:03 + place 25:05 +
  phys_opt 3:42 + route 36:15 ≈ **1:27** total; WNS −0.055 ns.
- **QoR path** (default parallel set): an ML-off safety placement is included
  to preserve the known-good QoR.  Stage 1 is bounded by the safety place,
  stage 3 by the safety route.  The +0.056 ns result above is from the known-good
  ML-off **1-thread** placement; the default 2-thread variant was still under
  validation at the time of this measurement.  If it does not reproduce the
  QoR, set the safety spec to `ExtraTimingOpt:off:1` (≈1:57 total).

`Explore` is not usable from the ML-on placement on this design: the router
fails while depositing pin assignments, reporting a solution overlap on
`SLICE_X115Y88`.  The default route remains `Default`.

### End-to-end timing (Vivado only; excludes `make build`)

| path | synth + opt | place | phys_opt | route | total |
|:--|--:|--:|--:|--:|--:|
| old final (ML off, 1t) | 22:03 | 42:45 | 1:45 | 47:52 | **2:03** |
| fast ML-on (1 candidate) | 22:03 | 25:05 | 3:42 | 36:15 | **~1:27** |
| QoR safety (ML off 1t) | 22:03 | 42:45 | 1:45 | 47:52 | **~1:54** |
| QoR safety (ML off 2t) | 22:03 | ~35:00 | ~4:00 | ~48:00 | **~1:49** |

The 3-candidate parallel flow has the same wall time as the slowest candidate
in each stage, not the sum of the candidates.  The safety path is the wall-time
floor because it deliberately runs the ML-off placement and route.


## 8. Risks and limits

| Risk | Mitigation |
|:--|:--|
| Vivado ML teardown/route SIGSEGV | Checkpointed stages, automated retry, ML-off/2-thread fallback, `hs_err` capture |
| `-ultrathreads` changes placement results | It is a candidate, not a forced replacement; the best WNS wins |
| 3 concurrent runs exhaust memory | 16 GB/candidate budget, 6 GB reserve, auto-clamp on `MemAvailable`; swap is a safety net, not a target |
| Route QoR depends on placement | Place diversity is explored before routing; if WNS is marginal, add route directives or the fallback recipe |
| Project run hardcodes 2 threads | `STEPS.*.TCL.PRE` hooks; the parallel flow bypasses project runs for place/route |
| Repeatability | `-ultrathreads` and ML can change results; record directives and keep the generated DCPs |
