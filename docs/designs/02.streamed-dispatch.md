# Design 02 — Streamed-matmul dispatch (NpuProgramEngine)

!!! warning "Partly superseded — see 04.streamed-issuing.md"
    This document is the early *high-level* overview of the streamed-dispatch
    idea, kept for motivation.  **The authoritative issuing model is
    [`docs/designs/04.streamed-issuing.md`](04.streamed-issuing.md).**  For
    exact structure and constants — the per-VX **W-bit `vxWrMask` + `vxWrCap`**
    scoreboard (not a single `vxWrTag`), the **DMA queue depth of 4**, the
    **K-deep** vd FIFO and capture queue, **`CAPTURE_DELAY = 16`**, the
    **`6K−1`** boundary countdown, and the **fetch engine → instruction FIFO
    (depth 8) → issue stage** frontend — use `04`.

## 1. Motivation

The previous engine was a single in-order issue unit with a stall FSM
(`IDLE → DMA_REQ → DMA_WAIT → DONE_1`): one instruction at a time, the DMA
blocked the MMALU and vice versa, and all inter-instruction timing (collector
drain before store, boundary between rounds, capture-before-store) was the
**software's** job via NOP padding and issue-timing-pinned capture columns.
Silicon divergences (cache-line fill gaps, stale operand feeds) repeatedly
broke those software-pinned timing assumptions.

The dispatch replaces the stall FSM with:

* a parameterized **issue window** of decoded micro-ops,
* a **scoreboard** over the physical register array (VX slots; VE/VR alias into
  VX), tracking pending producers and in-flight readers,
* **concurrent execution units** (DMA, MMALU), each with its own queue, and
* **producer/consumer chaining** so the dataflow of the stream paces the
  hardware — no software timing knowledge.

## 2. The single streamed-matmul mechanism

One mechanism covers every program — the one-shot, multi-mma, and chained
rounds alike — with zero NOP padding:

```
vle8   a0 → VX[4]        # producer: the RF write (DMA)
vle8   b0 → VX[8]
mma    vd0, 4, 8, 0      # consumer of a0/b0; producer of the capture
vle8   a1 → VX[4]        # WAR: waits until the previous mma fed on VX[4]
vle8   b1 → VX[8]
mma    vd1, 4, 8, 0
...
mma.last 0, 0, 0, 0      # session terminator + boundary (PE reset)
vse32  vd0 → OUT+0       # consumer of capture vd0 (chained on its clct)
vse32  vd1 → OUT+64
...
```

Each `mma`'s collector pulse captures the array's **running partial sum** of
the feeds settled by then.  The chained `vse` stores that value and consumes it
at the capture instant, so the destination register slot is free immediately
(the software's `vd` allocation is a pure software concern — any ring size
works).  Because operands chain through the scoreboard, the feed cadence is the
operand-arrival cadence, so the software never has to encode hardware timing.
