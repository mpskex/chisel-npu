## 2. The contamination (all confirmed by probes)

- Operands (A/B) are correct in the RF at feed time on silicon (probe p9).
- The sim (engine harness, frontend harness, latency-swept RAM) is clean at
  every L3 read latency 1..128 (NpuProgramEngineTimingSpec).
- The contamination is deterministic per absolute issue phase; clean phases
  are a minority and shift between builds/bitstreams.
- Dirty captures have the form `g[i] = a[i]·s + R[i]` with per-lane residue
  waves and the 3-mma captures being "two-column sums"
  `g[i] = a_m[i]·(b[c]+b[c+1]) + 7k`.

### The key sim-vs-silicon divergence (trajectory instrumentation)

Collector `{keep, dat_clct, cnt}` frozen 16-tick window (ctrl 0x20/0x24/0x28/0x2C):

| signal (session window) | SIM | SILICON |
|:---|:---|:---|
| `ctrl.keep` | 1 (accumulate) | **0** (overwrite) |
| collector `dat_clct` | HIGH | **LOW** |
| collector `cnt` | counting 1..15,0 | **0** (frozen) |

With `keep=0` the PEs run `res := in_a·in_b` (overwrite) and the collector's
`dat_clct` never opens, so the cnt stays 0 and the captured column is an
anti-diagonal/phase-dependent read.  The sim's keep=1 (with a single 1-tick
boundary pulse) is what produces clean uniform columns.

### Cautions before trusting the keep=0 reading
- `probe16.py` decodes entry[15] as `0x2C & 0x3F` — that is the **pad**, not
  the trajectory (must be `(0x2C >> 26) & 0x3F`).  The keep=0 conclusion
  rests on entries[0..14], which ARE correctly decoded — but re-verify on a
  known-good bitstream.
- The keep bit is only meaningful on the **6-bit** trajectory build.  All
  bitstreams loaded before the 11:02 full build were built from the stale
  Aug-9-20:40 synth (5-bit trajectory) — see §4.  The "keep=0" reads on those
  were reading the 5-bit dc bit into the "keep" field (artifact).

## 3. Changes made this session

### `src/main/scala/engine/npuProgramEngine.scala` — boundary-pulse fix
Replaced the clct-dependent boundary (`lastCapturePending` +
`boundaryPending` set on `mmalu.io.clct && lastCapturePending`) with a
**self-timed engine-local one-tick pulse**:

```scala
val boundaryCnt   = RegInit(0.U(6.W))
val boundaryPulse = RegInit(false.B)
when (mmaFeed && dec.mma_last) { boundaryCnt := (2 * K).U }
when (boundaryCnt =/= 0.U)     { boundaryCnt := boundaryCnt - 1.U }
when (boundaryCnt === 1.U)     { boundaryPulse := true.B }
when (boundaryPulse)           { boundaryPulse := false.B }
...
mmalu.io.ctrl.keep      := !boundaryPulse
```

Rationale: the boundary (keep=0 PE reset) must last exactly one tick, fired
2K ticks after the mma.last feed (after its clct/capture write).  It no
longer depends on the MMALU clct/keep interaction suspected on silicon.

## 7. The "silicon keep=0" story was an artifact (evening session)

- The trajectory ctrl map (0x20..0x2C) was **never in any bitstream**: firtool
  DCE'd it because `io.ctrl_addr` was `UInt(5.W)` — `ctrl_addr === 0x20.U` is
  provably false for a zero-extended 5-bit input → branches + ports pruned.
  Repro'd with `make build` + grep (no `5'h20` in the mux).
- Second layer: `npu_engine_subsys.v` declared `wire [4:0] ctrl_addr` —
  truncating the 7-bit ctrl_lite output → Vivado DCE'd the map in OOC synth
  (verified via DCP dump: 0 trajSnap cells).
- probe16.py's reads were **aliased**: 0x20/0x24/0x28/0x2C mapped to
  CTRL/FRAMES/STATUS/ERR_INFO (5-bit masking) — the "keep=0, dc=L, cnt=0"
  was STATUS/pc bits, and "entry[14]=kL11..15 counting" was `pc>>2`.
- Fixed: `npuFrontend.scala` ctrl_addr → `UInt(7.W)`; `npu_engine_ctrl_lite.v`
  + `npu_engine_subsys.v` → 7-bit ctrl_addr; 0x28/0x2C branches made exactly
  32 bits (0x28 had a 38-bit Cat that truncated traj(10); 0x2C a 33-bit Cat
  that dropped the keep bit).  Add `dbg_clct` passthrough on the frontend.
- `NpuProgramEngineFrontendSpec` now asserts the ctrl 0x20..0x2C trajectory
  readback (keep=1, dc=H, cnt = full 0..15 rotation) — guards the DCE trap.
- On the rebuilt bitstream the trajectory reads **sim-like**: keep=1, dc=H,
  cnt counting, for every probe16 run.  Engine-side control is correct.

## 8. Root cause #1 (FIXED + silicon-validated): the mma_last VX[0] feed

- `mma_last` (vs1=vs2=0) is dispatched by the engine as a **data feed** —
  `in_a = VX[vs1] = VX[0]`, `in_b = VX[vs2] = VX[0]`.  Sim only stays clean
  because VX[0] resets to 0.  On silicon VX[0] holds stale data (any earlier
  program that loaded VX[0], e.g. `test_illegal_instruction_halts`'s
  `vle8(0, ...)`), so every capture gets `VX0[i]·VX0[c]` added — the
  observed per-lane residue waves / phase-dependent contamination.
- Proven on silicon (probe19): VX[0]=zeros → 5/5 PURE; VX[0]=0x7F → 4/5
  captures exactly `+V0[i]·V0[c]`; ramp/all2/0x55 → residue present
  (phase-dependent).
- **Fix** (`npuProgramEngine.scala`): `in_a/in_b := Mux(mmaFeed && !dec.mma_last,
  VX[...], 0)` — mma_last is a terminator marker, feeds zeros (parallel to
  the existing vs3==0 accum zero-forcing).  Comment updated.
- Regression: `NpuProgramEnginePhaseSweepSpec` — 24-phase one-shot sweep
  (asserts all clean) + a VX[0]-loaded contamination test (asserts clean;
  verified it FAILS without the fix).
- Silicon validation: probe16 12/12 clean, probe19 25/25 PURE, exact-test
  probe 30/30 clean, `pytest -m hw` 6 passed / 1 xfailed (3× stable).
- `test_one_shot_session`: xfail marker REMOVED.
