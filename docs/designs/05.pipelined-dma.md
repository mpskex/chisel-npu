# Pipelined / Outstanding DMA — Design Proposal

**Status:** proposal, not implemented
**Date:** 2026-11-14
**Branch:** `fangrui/refine-dispatch-frontend`
**Measured context:** `docs/implementations/FPGA_VU9P.md` — “MACs/cycle: feed
scaling and the path to 1K”

## 1. Why

The measured instruction-supply and feed studies isolate the remaining
bottleneck of the matmul round shape:

| shape | cycles | MACs/cycle | note |
|:--|--:|--:|:--|
| `round-256` (immediate store) | 29,867 | 280.9 | store RAW wait (~81 cyc) |
| `pipe-256` (store delayed 4 rounds) | 20,136 | 416.6 | DMA-bound |
| `feed-8,192` (one capture) | 8,559 | 980.1 | array/feed path |
| `feed-65,531` (one capture) | 66,656 | **1,006.7** | 98.3% of K²=1,024 |

The software store pipeline removed the store’s RAW wait on the capture. The
remaining `pipe-256` time is almost exactly the shared DMA:

- 256 `vse` stores + 137 instruction-fill requests = **393 DMA requests**
- 20,136 cycles / 393 = **51.2 cycles per request**

`NpuDmaEngine` processes one request at a time. Its one-deep request buffer only
overlaps the **address phase** of the next request with the current **data
phase**; the burst latency itself (read data / write response) is not overlapped
with another burst. In the long feed stream the 1,025 fills/stores are hidden
behind 65.5 k feed cycles (the DMA is not visible); in the round shape the DMA
is the critical resource.

The target: hide the ~51-cycle request latency with 2–4 outstanding AXI
transactions, overlapping the read and write channels, so `pipe-256` approaches
the feed/issue limit (~900–960 MACs/cycle) instead of 416.6.

## 2. Current implementation (baseline)

**`src/main/scala/dma/npuDmaEngine.scala`**

- Request types: `dir=0` (L3→VX), `dir=1` (VX→L3), `dir=2` (L3→ACCUM),
  `dir=3` (L3→instruction line, 1–4 beats).
- FSM: `IDLE → AR → READ → RFW/ACCW/INSTRW → DONE` for reads;
  `IDLE → WAW → WDATA → WRESP → DONE` for writes.
- One in-flight burst. A one-deep `buf*` captures the next request when
  `req_ready` rises after the current data phase starts; the next request is
  promoted only when the FSM returns to `IDLE`.
- `busy = state =/= IDLE || bufValid`; `done` is a one-cycle pulse at `DONE`.
- Read/write timeout retries; 512-bit AXI; the `buf` holds `MAX_BEATS = 4`.

**`src/main/scala/engine/npuProgramEngine.scala`**

- `dmaQ` depth 8 (`DmaEntry`: valid/inFlight/tag/dir/dmaWidth/rfAddr/l3Addr/
  rdMask/storeDataValid/storeData/dataReady/beats).
- `dmaAccept` presents the queue head (`valid && !inFlight && dataReady`);
  `dmaDoneHead` retires the head on `dma.io.done && inFlight`.
- Fetch fills (`dir=3`) are queued as `dmaQ` entries with a placeholder tag 0;
  `fillPending` gates one fill at a time; `fetch_fill_valid/last` are derived
  from `dma.io.instr_valid/instr_last` and the head’s `dir===3`/`inFlight`.
- Tags: T=128 ring (`tagValid/tagFed/tagCount/tagTail`); the tag is freed at the
  capture completion for `mma.last` and at `dmaDoneHead` for DMA entries.
  `wrDone`/`rdDone` counters track the register hazards.

The current completion is strictly in order: one request, one `done`, the head
retires. That is the property this design changes.

## 3. Goals

1. **2–4 outstanding reads and writes** across the single AXI master, with the
   read and write channels able to progress independently.
2. `pipe-256` ≥ ~900 MACs/cycle (from 416.6) without changing the ISA, the
   driver API, the ctrl register map, or the external AXI port list.
3. Keep the long-feed result (≥1,006 MACs/cyc) and `py-test-hw` 8/8.
4. Preserve the register hazard ordering (loads/stores/feeds/captures),
   fetch-fill ordering, and the abort/epoch behavior.
5. 100 MHz timing closure (current WNS +0.056 ns; gate −1.0 ns).

## 4. Non-goals

- The exact 1,024 MACs/cycle round boundary (the `mma.last` zero feed and
  capture-only reset are a separate ISA/microarchitecture change; see
  `FPGA_VU9P.md` step 5).
- Changing the DDR4 MIG, the 512-bit AXI data width, the XDMA/ctrl path, or the
  100/250 MHz clocking.
- A general-purpose cache/coherence layer; the data sections remain
  software-managed.

## 5. Approaches

### A. Split read/write engines + outstanding descriptors + ordered retire (recommended)

Two independent channel engines (read and write), each accepting up to
`OUTSTANDING=2..4` descriptors from a shared descriptor FIFO. The read and
write channels overlap; the descriptor completions are collected in a small
reorder queue so the engine retires `dmaQ` entries in order (preserving the
existing tag/counter ordering), while the AXI bursts themselves overlap.

- Gain: hides both the read and write burst latencies; the round’s 393 requests
  are no longer serialized at 51.2 cycles each.
- Cost: the DMA FSM split, a descriptor/reorder queue, the engine completion
  path, the abort/flush, the fetch-fill routing.

### B. Keep one FSM, deepen the request buffer only

Replace the one-deep `buf` with a 2–4 entry request FIFO but keep one burst in
flight. The address phases overlap, but the burst latency still serializes.
Expected gain is small (the current one-deep buffer already overlaps the
address phase); it does not remove the 51.2-cycle wall. **Rejected as the main
path**, but useful as an intermediate commit/test harness.

### C. Store coalescing only

Merge four adjacent 128 B `vse` writes into one 512 B write (256 stores → 64
requests). The request count drops, but each request still costs ~51 cycles and
the fetch requests remain; the standalone ceiling is ~820 MACs/cycle.
**Useful complement to A**, not a substitute.

**Chosen: A, with C as an optional later optimization.**

## 6. Detailed design (Approach A)

### 6.1 Descriptor queue

Reuse the engine’s `dmaQ` as the descriptor source (depth 8; the current
single-writer tail rules still apply). The DMA accepts a descriptor when a
read/write engine slot is free, not only when the whole DMA is idle. A
descriptor carries the existing `DmaEntry` fields plus a small **sequence
number** (2–3 bits wrapping) identifying its position in the retire order.

- `req_ready` becomes the OR of the free-slot conditions for the descriptor’s
  direction (read vs write), not a function of a single global `IDLE`.
- The engine marks the descriptor `inFlight` on acceptance as today; the
  descriptor can be completed out of order in the AXI, but the **engine
  retire** is ordered by the sequence number.

### 6.2 Read engine

- Accepts up to `R_OUT=2..4` read descriptors (dir=0/2/3).
- Issues `AR` for each free descriptor; tracks the beat count and the
  destination (`VX/VE/VR`, `ACCUM`, `INSTR`).
- Streams `R` beats into the descriptor’s destination buffer; the current
  per-beat `buf` becomes per-descriptor beat storage. The VR read needs 2 beats;
  the fetch needs 1–4; the VX/VE 1.
- Emits one completion event (descriptor sequence, tag, `done`, the
  `instr_valid/instr_last` for dir=3) when `RLAST` has been consumed and the
  destination write/line commit is done.

The read data for a dir=3 fetch is the existing `instr_out` 512-bit path. The
engine’s `fetch_fill_valid/last` must be derived from the **dir=3 descriptor’s**
completion, not from “the queue head is dir=3”: with outstanding data reads, the
head may be a data request while the fetch descriptor is in flight. Keep the
frontend’s one-fill-at-a-time `fillPending` (the frontend still serializes its
line fills); the DMA may have other data reads outstanding around it.

### 6.3 Write engine

- Accepts up to `W_OUT=2..4` write descriptors (dir=1).
- Issues `AW`/`W` with the already-snapshotted `storeData` (the `vrPending`
  path is unchanged; the store data is captured at issue, not at DMA time).
- Tracks the `B` response; emits one completion event per descriptor.
- The write channel is independent of the read channel: a `vse` store can be in
  its `B` phase while a `vle`/fetch read is in its `R` phase.

### 6.4 Ordered retire and tags

The engine retires the `dmaQ` head when its sequence has completed. A small
**reorder queue** (depth `OUTSTANDING+1`) buffers completion events; the head
is retired when its event is present. This preserves:

- `dmaDoneHead`-style tag free and `wrDone/rdDone` increments in program order.
- The `tagValid/tagFed/tagCount/tagTail` ring semantics (out-of-order frees are
  not required; the tags are freed at the ordered retire).
- The fill’s `fillPending` clear and the deferred VR store’s completion.

If measurements show the ordered retire delays a producer’s `wrDone`/`rdDone`
behind an unrelated earlier request, the alternative is a per-descriptor
completion with a **tag free-list** (a 128-bit free bitmap + priority encoder)
and direct counter updates; that is a second-phase optimization, not the first
implementation.

### 6.5 Abort / epoch

`session_reset` and `illegalAny` flush the engine’s `dmaQ` and clear
`fillPending`. With outstanding AXI bursts, the DMA also needs a **flush**
input:

- Stop accepting descriptors; drop the buffered/queued descriptors.
- Let the in-flight AXI bursts drain (the AXI has no cancellation); discard
  their data/completions via an **epoch bit** carried per descriptor (or a
  flush sequence), so a stale `R`/`B` cannot commit to a new session.
- The engine’s `fetch_fill_valid` is gated by the descriptor’s epoch/inFlight,
  as the current head/inFlight gate does for an aborted fill.
- The final abort-hardening behavior (serialize a post-abort fill behind DMA
  idle) remains the safe fallback if the flush path is not ready.

The DMA must never hang on a dropped descriptor: the read/write timeout/retry
logic drains the AXI, the flush clears `busy`, and `dmaQ` is reset to the tail.

### 6.6 AXI details

- Keep the external 512-bit AXI port list unchanged.
- Use AXI IDs per channel if the MIG requires them for outstanding ordering;
  otherwise a single ID with in-order responses per channel is sufficient
  (reads return in request order per ID; writes’ `B` returns in order per ID).
- The read/write channels are independent by AXI construction; the current
  single FSM’s serialization is an implementation choice, not an AXI limit.
- Preserve the read timeout/retry and the write `B` timeout/retry states per
  outstanding descriptor, or drain the channel on a timeout before accepting a
  new descriptor.

### 6.7 Store coalescing (optional, Approach C)

The four `vse32` stores of a 4-vd ring target adjacent 128 B OUT blocks. The
write engine can merge consecutive write descriptors with contiguous addresses
into one 512 B (8-beat) write:

- 256 stores → 64 requests; the fetch 137; total 201 requests.
- Alone: ~201 × 51.2 / 256 = 40.2 cycles/round → ~819 MACs/cyc.
- With outstanding (A): the stores stream; the round approaches the feed/issue
  limit.
- Requires write-descriptor merging, one completion for the merged group, and
  the four tags freed together; the store data snapshots are already per-entry.

## 7. Expected performance

Model (per `pipe-256`): 393 requests, 51.2 cycles each serial; the read 4-beat
fill and the 2-beat write.

- With 2–4 outstanding and read/write overlap, the effective per-request cost
  drops toward the AXI beat/response rate; the round’s 33 feeds + issue can
  then dominate.
- Target: `pipe-256` **~9–12 k cycles → ~850–960 MACs/cycle**; the long-feed
  result must stay ≥1,000.
- With store coalescing: further margin; with the issue/last changes
  (`FPGA_VU9P.md` steps 4–5): 993 / 1,024.

The design does not change the array or the frontend; the feed path is already
at 1,006.7.

## 8. Verification

**Unit / simulation**

- `NpuDmaEngineSpec`: add tests for 2 and 4 outstanding reads, 2 and 4
  outstanding writes, read/write overlap, response ordering, timeout/retry,
  and a flush during outstanding traffic (no stale commit, `busy` clears).
- A reorder/tag test: complete descriptors out of order; the engine retires in
  order; the tags/counters match.
- Fetch-fill test: a dir=3 fetch in flight while a data read and a write are
  outstanding; the `instr_valid/last` route to the right descriptor; the
  frontend’s `fillPending` clears once.
- Existing: `NpuProgramEngineFrontendSpec`, `FetchAbortSpec`,
  `EnginePerfCounterSpec`, `EngineThroughputSpec`, `Streamed*`/`Capture*`.

**Hardware**

- Build, WNS ≥ −1.0 ns; program; `py-test-hw` 8/8; selftest.
- `fetch_sweep.py`: `pipe-256` ≥ ~800 MACs/cycle target; `feed-65531` ≥ 1,000;
  `round-256` improves; the NOP slope stays flat.
- Max-length program (65,535 words) and the abort/restart path.

## 9. Risks and mitigations

| Risk | Mitigation |
|:--|:--|
| AXI outstanding support/ordering in the MIG | Start with 2 outstanding, single ID per channel; verify with the DMA unit tests and the hardware suite; ask the MIG for out-of-order only if needed |
| Tag/counter out-of-order hazards | First implementation uses ordered retire + a small reorder queue; the free-list is phase 2 |
| Abort with outstanding bursts | Epoch/flush + drain; keep the current post-abort fill serialization as fallback |
| Timing at 100 MHz | Split the read/write FSMs; keep the descriptor/reorder queues small; measure WNS after each phase |
| Fetch/fill routing | Per-descriptor dir=3 signals; keep the frontend’s one-fill-at-a-time |
| Store coalescing complexity | Optional, after the outstanding DMA works |
| Shared AXI bandwidth | The measured store+fetch payload is ~8 B/cycle; the 512-bit AXI at 100 MHz is 64 B/cycle; latency, not bandwidth, is the wall |

## 10. Implementation phases

1. **Read/write channel split** (keep 1 outstanding per channel): separate the
   read and write FSMs; the read and write can overlap. Tests: overlap, no
   ordering regression.
2. **2 outstanding per channel + reorder retire**: the first performance
   measurement; `pipe-256` target ≥ 700; the hardware suite.
3. **4 outstanding + abort/flush + fetch routing**: the main target
   (~900–960); the full tests.
4. **Store coalescing** (optional): 256 stores → 64; measure.
5. **Issue/last** (separate, for 993/1,024): the `vrPending` bubble, dual-issue,
   capture-only boundary.

Each phase is independently testable and buildable; do not combine phases 1–3
in one bitstream without the intermediate measurements.

## 11. Open decisions

- Ordered retire vs a per-descriptor tag free-list (phase 1 vs phase 2).
- Read/write outstanding depth (2 vs 4); start at 2, measure.
- AXI IDs/in-order per channel vs multiple IDs.
- Store coalescing (phase 4) — worth the complexity after the outstanding DMA.
- The exact-1K capture-only boundary — a separate ISA/microarchitecture design.
