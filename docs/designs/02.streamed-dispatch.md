# Design 02 — Streamed-matmul dispatch (NpuProgramEngine)

Status: approved 2026-08-10 (supersedes the stall-based dispatch of
handoff-2026-08-09/10).  One mechanism for every program: a software
**streamed matrix multiplication** executed by a windowed scoreboard dispatch
with producer/consumer chaining.  No NOP padding, no software timing
knowledge, no special "drained capture" case.

## 1. Motivation

The previous engine was a single in-order issue unit with a stall FSM
(`IDLE → DMA_REQ → DMA_WAIT → DONE_1`): one instruction at a time, the DMA
blocked the MMALU and vice versa, and all inter-instruction timing (clct
drain before vse, boundary between rounds, capture-before-store) was the
**software's** job via NOP_WAITs and issue-timing-pinned capture columns.
Silicon divergences (cache-line fill gaps, stale VX[0] feeds) repeatedly
broke the pinned assumptions.

The dispatch replaces the FSM with:

* a parameterized **issue window** (W slots, default 16) of decoded micro-ops,
* a **scoreboard** over the physical register array (VX slots; VE/VR alias
  into VX), tracking pending producers and in-flight readers,
* **concurrent execution units** (DMA, MMALU; a future VALU slot), each with
  its own queue, and
* **producer/consumer chaining** so the dataflow of the stream paces the
  hardware — no software timing.

## 2. Instruction stream model (the single mechanism)

```
# streamed matmul round — one mechanism for the one-shot, n-mma, 32-mma,
# and chained rounds alike; zero NOP padding
vle8   a0 → VX[4]        # producer: the RF write (DMA)
vle8   b0 → VX[8]
mma    vd0, 4, 8, 0      # consumer of a0/b0; producer of the capture
vle8   a1 → VX[4]        # WAR: waits until the previous mma fed on VX[4]
vle8   b1 → VX[8]
mma    vd1, 4, 8, 0
...
mma.last 0, 0, 0, 0      # session terminator + boundary (PE reset)
vse32  vd0 → OUT+0       # consumer of capture vd0 (chained on its clct)
vse32  vd1 → OUT+64
...
```

Each `mma`'s clct (2n−1 ticks after its feed) captures the current array
column — the **running partial sum** Σ_{m≤k} a_m·b_m of the feeds settled by
then.  The chained `vse` stores that value; the value is consumed at the
capture instant, so the destination register slot is free immediately (the
software's vd allocation is a pure software concern — any ring size works).

## 3. Dispatch architecture

### 3.1 Issue window (parameterized `W`, default 16)

A ring of W slots.  Each slot holds the decoded micro-op + its issue state:

```
{ valid, unit, family, rd, rs1, rs2, vs3, memWidth, sect, off,
  isStore, isMmaLast, illegal,
  issued, done,
  useCaptureData }               # vse: source produced by an mma capture
```

* `instr_ready` = the window has room (the frontend FSM is unchanged; it
  streams words at its own pace).
* The **oldest ready slot issues** each tick (in-order stream; the unit
  queues preserve the order).
* NOPs retire on entry; ILLEGAL slots pulse `io.illegal_out` and halt (the
  frontend latches pc/ERR_INFO as before).

### 3.2 Scoreboard (physical-register granularity, L VX slots)

Alias-aware: `VE[i] → VX[2i..2i+1]`, `VR[i] → VX[4i..4i+3]`.  One mechanism
for every register class — the same structure a future VALU will use.

Per VX slot:

* `vxWrTag`      — window index of the pending producer (vle DMA write or
  mma capture), or none.
* `vxWrCapture`  — producer type bit (capture vs RF write).
* `vxRdMask`     — window slots currently waiting to READ the slot.

Reads/writes per instruction:

| instruction | reads | writes |
|:---|:---|:---|
| vle(rd)   | — | VX[rd] |
| mma(vs1, vs2, vd) | VX[vs1], VX[vs2] (at the feed) | VX[4vd..4vd+3] (capture) |
| vse(src)  | the source register (RF read at the DMA beats) | — |
| VALU (future) | per-op | per-op |

**Readiness** of slot s (all must hold):

1. **RAW**: every slot s reads has `vxWrTag == none` or `vxWrTag == s`
   (a consumer never waits on its own capture).
2. **WAR**: every slot s writes has `vxRdMask ∩ prior(s) == ∅` (prior =
   valid slots earlier in the stream; the producer waits for earlier
   readers that read the old value).
3. Unit room: the DMA queue (LD/ST) / the MMALU FIFO + capture queue (mma).
4. **Boundary gate**: an mma-family slot requires `boundaryCnt == 0`
   (see §5).

**Completion** clears the tags:

* mma feed → its read bits in `vxRdMask` cleared.
* vle DMA done → `vxWrTag` cleared (only if it still points at this slot),
  slot retired.
* mma clct → the capture: `vxWrTag` for VX[4vd..4vd+3] cleared, the
  capture value pushed to the capture-data queue, slot retired.
* vse DMA done → slot retired (its read bits were cleared at the issue for
  capture data, or at the DMA beats for RF data).

### 3.3 Execution units

**DMA unit** — a dispatch-side request queue (depth 8):

```
{ dir (0=vle, 1=vse, 3=fetch-fill), width, rfAddr, l3Addr,
  useCaptureData, captureData (K×4N) }
```

One request at a time drives the existing `NpuDmaEngine` (unchanged), which
serializes with the frontend's fetch fills on the AXI master.

**MMALU unit** — the existing feed path + the vd FIFO (depth 2K+4) + the
capture-data queue (depth 2K+4, K×4N entries).  The mma issues one feed
tick; the FIFO pairs each feed's vd with its clct; the capture queue
carries the capture values for the chained vses.

**Future VALU slot** — the family→unit table is a single mux; the VALU
families decode but are marked ILLEGAL until the vector unit lands.

### 3.4 Chaining edges (the "right timing")

| edge | mechanism |
|:---|:---|
| vle(rd=X) → mma(vs1=X) | the DMA done (the RF write) clears X's tag; the waiting mma feeds on the next tick — the feed cadence = the operand-arrival cadence |
| mma(rd=vd) → vse(src=vd) | the clct (the mma's final tick) pushes the capture value into the capture-data queue and clears vd's tag; the vse (ready at the clct) pops the queue at its issue and its store entry carries the latched value — **the value is read right after the mma completes its final tick** || WAR (general) | a producer waits for earlier in-flight readers of its target (the vle waits for the prior mma feed reads; the general rule protects the future vector-unit traffic) |
| mma.last → next round | the boundary countdown (§5) gates the next round's first mma; the round's vle/vse DMAs proceed during the window |

The capture also writes VR[vd] (architectural state, kept for readback);
the vse's store data comes from the capture-data queue (capture-produced
sources) or the RF read (vle-produced sources).

### 3.5 Result routing (scalable, for the future vector units)

The dispatch's completion path is a generic **producer→consumer table**: a
unit completion carries a result tag (the written register set + the slot
id) and optionally a payload.  Consumers select their data source by the
producer type:

* capture producer (mma) → the capture-data queue (latched at the clct),
* RF producer (vle; future VALU) → the RF read (protected by the WAR).

The store-queue entry data width is K×4N — the widest register class — so a
future vector unit's results flow through the same vse path.

## 4. Semantics — one mechanism

* The capture at each clct = the array column at that instant = the running
  partial sum of the feeds settled by then.  The software computes the
  per-capture expectations (running sums); the final capture equals the
  full session product.
* **Capture-settle delay**: the MMALU's clct fires 2n−1 after a feed, but the
  pipelined systolic data settles ~δ ticks later (the 2026-07-30 pipe
  stages).  Sampling the collector at the clct instant reads the
  still-settling array (cadence-dependent partial columns).  The engine
  therefore samples the capture `CAPTURE_DELAY = 4` ticks after the clct —
  the collector output has settled by then and equals a clean running-sum
  column (the column index walks with cnt, so any settled column is fine —
  the tests/hw search the columns).  All capture completions (FIFO pop,
  slot done, wrMask clear, capture-queue push, VR write) move to the delayed
  tick so the chained vse pops the right value.
* **int8 signedness**: the operands are int8 bytes; the PE multiplies
  SIGNED.  Values ≥ 128 (0x80..0xFF) are negative — the expected running
  sums must use the `s8` interpretation, exactly like the hardware tests.
  (The one-shot/3-mma tests with small operands masked this.)
* The feeds are paced by the operand loads (the vle chaining) — the fetch
  cadence (cache-line fills) merely delays feeds; the captures stay clean
  running sums (verified across RAM latencies 1..200 in simulation).
* Register reuse (vd rings, operand slots) is entirely the software's job;
  the hardware never stalls on reuse beyond the scoreboard's WAR/RAW.
* The boundary (PE reset) between rounds is hardware-gated (§5) — rounds
  chain back-to-back with zero software padding.

## 5. Boundary gate

`boundaryCnt` (7 bits — also fixes the latent K=32 overflow of the old 6-bit
counter):

```
mma.last feed        → boundaryCnt := 4K − 1
every tick           → boundaryCnt -= 1   (while ≠ 0)
keep = 0 pulse       → boundaryCnt === 2K (one tick, 2K after the feed —
                       after the last capture at 2n−1)
mma-family readiness → boundaryCnt === 0
```

The keep=0 pulse resets the PEs; the diagonal reset wave completes at
2K + 2n − 2; the gate (4K − 1) adds one tick of margin.  The next round's
first feed can therefore issue immediately after the countdown, with the
round's vle/vse DMAs running concurrently during the window.
